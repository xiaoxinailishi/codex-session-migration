# Codex Session Migration

[简体中文](README.md) · [Quick start](docs/QUICKSTART.zh-CN.md) · [How it works](docs/HOW-IT-WORKS.md) · [Troubleshooting](docs/TROUBLESHOOTING.md)

Move selected **local Codex conversations and user-uploaded images** between Windows computers or between `CODEX_HOME` locations. Includes backup and restore, image recovery, offline import, and one-way refresh with a previous-export baseline.

This community project documents methods and fixes from a real migration, without publishing that user's projects, conversations, images, credentials, device names, or network addresses. Migration packages generated by the tool contain the selected private conversations and must remain private.

This is **not an official OpenAI migration API**. It uses internal SQLite and JSONL formats. Unknown schema differences stop the operation. Requires Python 3.11+; no third-party runtime packages. Publishing to live databases currently supports Windows only.

## Workflow

1. Run `inventory` on the source. Select thread UUIDs or an exact project root.
2. Run `export`, supplying source-to-target project mappings. Source records remain unchanged.
3. Privately copy the package to the recipient. Register the target project in Codex. Run `check-package` and `prepare` to build validated copies.
4. Open a separate PowerShell terminal, completely quit Codex, then run `apply --confirm` with the returned `prepared_root`.
5. Run `verify`; start Codex and inspect the imported conversations, project assignments, and images.

From the repository root:

```powershell
python -m codex_migrate inventory --home C:\Data\CodexSource
python -m codex_migrate export --home C:\Data\CodexSource --thread 00000000-0000-4000-8000-000000000001 --map "C:\Projects\demo=D:\Projects\demo" --output C:\Transfer\run-a
python -m codex_migrate check-package --stage D:\Transfer\run-a
python -m codex_migrate prepare --home D:\Data\CodexTarget --stage D:\Transfer\run-a
# After completely quitting Codex, substitute the actual prepared_root:
python -m codex_migrate apply --home D:\Data\CodexTarget --prepared "D:\Transfer\run-a\prepared-<actual-value>" --confirm
python -m codex_migrate verify --stage D:\Transfer\run-a
```

All paths and UUIDs above are fictional. Copy `manifest.json` and the complete `payload` directory together. For ZIP transfer use `serve` / `receive`; copying a ZIP alone does not create an import stage. If SQLite is stored separately, pass `--sqlite-home` explicitly or let the tool read `config.toml` and `CODEX_SQLITE_HOME`.

## Preservation and limitations

The exporter selects session records and user image bytes, excluding project files and authentication files. It recovers original image files when available, otherwise the bitmap actually transmitted in user messages. A transmitted bitmap may differ from an expired original; missing or ambiguous images stop the export.

Preparation preserves unrelated rows, the recipient's project registry, and unrelated desktop state. It rewrites structured image references and rebases JSONL byte offsets without substituting paths in historical prose. Refresh stops when the recipient's selected conversation diverges from its baseline. This is not bidirectional merge or continuous synchronization.

Publication backs up live targets and guards against changes since preparation. Later work prevents a manual rollback. Cleanup is a separate action: inspect the plan, select exact entries, and confirm; rollback backups are kept by default and live image roots are protected.

Internal storage varies between releases. See [compatibility](docs/COMPATIBILITY.md) and [troubleshooting](docs/TROUBLESHOOTING.md). Active turns, non-image attachments, unfamiliar schemas, and missing desktop project registration stop this version.

## Validation

```text
python -m unittest discover -v
```

Tests use synthetic SQLite databases, fictional chats, and one tiny PNG. They verify recovery, refresh guards, rollback and cleanup, while mocking the Windows offline process check. Passing tests demonstrate these cases; they do not demonstrate acceptance in your Codex UI. Original migration methods were exercised in a real migration; the generalized tool must still be rehearsed against your version.
